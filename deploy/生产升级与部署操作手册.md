# 生产升级与部署操作手册

本手册适用于已部署的独立运行生产环境。每次升级由打包人员和现场操作人员核对本版变更后执行；初装、新环境及 Docker 环境须另行核对部署方式，不能直接套用本文。操作记录应包含包名、版本、时间、目标库、备份位置、执行人及结果。

## 一、环境与分工

- **67（192.168.1.11）**：平台（nginx、后端、前端、采集 Worker）与 **MySQL 数据库及客户端**同机部署；平台入口为 `http://192.168.1.11:8080/metric-code/`。备份、迁移和平台升级都在 67 执行。
- **66（192.168.1.10）**：原数据库服务器，**已停用下线**（用户于 2026-11-21 确认），不再作为目标库或备份来源。该拓扑由用户于 2026-11-21 更新，替代 2026-11-19 的双机描述。
- 升级包不覆盖现场 `config/app.env` 和采集数据目录。涉及数据库迁移时先备份并在 67 完成数据库升级，再升级平台；不涉及数据库迁移时同样先备份再升级平台。不得手工补跑或改写 Flyway 历史。
- 现场安装目录、数据库名、账号、端口、备份路径和服务管理方式以实际环境为准，以下尖括号内容必须替换，勿把密码写入文档或命令历史。

## 二、开发机打包

1. 拉取并合并最新 main 后，核对交付代码、未提交变更、本次迁移、所需采集脚本版本和本版说明。工作区含未提交内容时，确认它们全部属于交付范围；记录提交号及实际交付内容。确保 Java 17、Maven、Node/npm、Python、Git Bash、tar 和 sha256sum 可用，前端依赖已安装。
2. **逐次核对外置采集脚本**：`deploy/scripts/build-upgrade.sh` 的 `SCRIPT_VERSIONS` 默认值是脚本中写死的历史版本，并不自动跟随最新绑定。核对本次迁移、采集任务绑定和 `catalog.json`，将本次需要随包安装的全部版本列入 `SCRIPT_VERSIONS`；历史环境已有版本也应核实。发布目录须有匹配的 manifest，版本不可覆盖。不要仅因为打包成功就认为版本齐全。
3. 在仓库根目录的 Bash 执行（以下版本名仅示意，替换为本次核对结果）：

   ```bash
   SCRIPT_VERSIONS="<版本一> <版本二>" bash deploy/scripts/build-upgrade.sh
   ```

   默认构建后端、前端及 Worker，产物位于 `deploy/out/metric-code-upgrade-<时间戳>.tar.gz` 和同名 `.sha256`。只有明确确认已有构建产物与本次代码一致时才可使用 `--skip-backend` 或 `--skip-frontend`。若本版还包括独立 Mock 更新、手工投递文件等，须按本版说明另行准备并核对；常规脚本不会自动包含这些内容。`build-reviewed-upgrade.py` 是特定批次脚本，不应当作通用打包命令。
4. 查看 `BUILD_INFO.txt`、压缩包内容、迁移和外置脚本清单，确保本版所需文件齐全；核对压缩包及校验文件，并将两者和本版说明传到 67。打包脚本显示的迁移数量来自源码目录，不能单独证明 jar 内容；需要时检查 jar 内 `BOOT-INF/classes/db/migration/`。

### 判断本次是否涉及数据库迁移

以现场正在运行的包及其对应源码提交为基准，比较本次实际交付代码中 `backend/src/main/resources/db/migration/` 的新增迁移及其他会改变结构或数据的升级动作。例如已知上次源码提交时，可运行 `git diff --name-status <上次交付提交> <本次交付提交> -- backend/src/main/resources/db/migration/`；另行检查未提交和未跟踪的交付文件。不得只比较 main 最新一次提交或仅按迁移数量判断。

再从 67 的实际 `config/app.env` 核对目标，在 67 只读核对实际表结构及 `flyway_schema_history` 的基线、已成功版本、失败记录和校验值，与本次 JAR 内迁移逐项比较。现场版本未知、历史缺失、乱序、校验不符或库结构不符时，按涉及数据库处理，先解决差异；不要将它们视为无迁移。历史迁移不得修改或伪造记录。

| 判断结果 | 升级顺序 |
| --- | --- |
| 有待执行迁移，或本版其他升级动作会修改数据库 | 打包本版核对过的数据库升级程序、依赖及迁移；先在隔离库演练。维护窗口暂停目标库写入，在 67 备份、核对并通过该程序受控升级；确认结果后再升级平台。 |
| 确认无待执行迁移，且本版没有其他数据库修改 | 沿用此前流程：67 核对和备份目标库，67 校验升级包后预演、升级平台（脚本内备份可正常执行，一般不加 `--skip-backup`）。后端启动时正常执行 Flyway 校验。 |

数据库升级程序与允许执行的版本必须按每次交付核对，不可把 2026-11-19 候选包中限定服务器 UUID 和版本清单的专用脚本直接用于后续版本。程序缺失、未经隔离环境演练，或迁移执行方式尚未明确时，不得交付为可执行的生产升级包。不要因为本次源码没有新增 SQL 就忽略目标库已有未执行迁移。

## 三、67：核对并备份目标数据库

从 67 现场 `config/app.env` 安全核对 JDBC 地址、端口、库名和账号，确认指向本机库（`127.0.0.1` 或 `192.168.1.11`），并排除仍指向已下线的 66 的旧配置。再在 67 上确认实际连接的是正确目标库。按数据库版本记录核对已使用的备份编号，本次使用更大的未占用 `V<n>`，不得覆盖。创建受限权限的备份目录（数据库与平台共用磁盘，先确认剩余空间），备份结构和数据：

```bash
set -o pipefail
umask 077
mkdir -p '<安全备份目录>/V<n>'
mysqldump -h 127.0.0.1 -P '<端口>' -u '<账号>' -p \
  --single-transaction --quick --routines --events --triggers \
  --default-character-set=utf8mb4 --databases '<目标库名>' \
  | gzip > '<安全备份目录>/V<n>/before-upgrade.sql.gz'
gzip -t '<安全备份目录>/V<n>/before-upgrade.sql.gz'
test -s '<安全备份目录>/V<n>/before-upgrade.sql.gz'
gzip -cd '<安全备份目录>/V<n>/before-upgrade.sql.gz' | tail -n 5
sha256sum '<安全备份目录>/V<n>/before-upgrade.sql.gz'
```

交互输入密码；确认命令全部成功、末尾包含 `Dump completed`，记录校验值、目标库和备份位置到 [数据库版本记录](../doc/数据库版本记录.md)。核实备份可取用且满足现场恢复要求；备份失败或目标不明则停止升级。升级前如有结构变更，必须完成上述结构及数据备份，且按项目备份台账规范记录。

本版涉及数据库迁移时，按本版经过验证的升级程序在 67 执行迁移；若程序自身完成备份，核实其备份范围、版本、完整性及台账，避免重复备份或遗漏。升级前停止平台及其他写入目标库的程序，按程序实际要求检查连接和锁；其他业务连接不得盲目关闭。确认数据库升级成功并检查实际结构或数据后，才进行第四节。无数据库迁移时，备份核实后直接进入第四节。

## 四、67：校验与升级

确认维护窗口、现场安装目录和磁盘空间；按本版说明处理需暂停的独立生成器或其他现场依赖，保留状态和数据。将升级包与 `.sha256` 放在同一目录：

```bash
cd '<升级包所在目录>'
sha256sum -c 'metric-code-upgrade-<时间戳>.tar.gz.sha256'
tar -xzf 'metric-code-upgrade-<时间戳>.tar.gz'
cd 'metric-code-upgrade-<时间戳>'
cat BUILD_INFO.txt
bash bin/apply-upgrade.sh --app-home '<现场平台目录>' --skip-backup --dry-run
bash bin/apply-upgrade.sh --app-home '<现场平台目录>' --skip-backup
```

校验、预演和目标路径正确后才执行正式命令，按提示确认。数据库与平台同机，脚本内 `mysqldump` 备份默认可正常执行，**通常不需要 `--skip-backup`**；仅当已另行完成并核实第三节备份时才使用该参数，它会跳过脚本内备份和库连通性检查。需要时按现场情况设置包内 `bin/apply-upgrade.sh` 顶部的 `JAVA17_BIN` / `MYSQL_BIN` / `MYSQLDUMP_BIN`；Java 必须为 17 或以上。

脚本会停止后端、备份旧程序至现场 `rollback/<时间戳>/`、安装外置脚本、替换程序并启动后端。它尝试重启 `metric-collection-worker.service`；若未检测到或重启失败，要根据现场服务方式手工恢复并检查。配置、采集历史及独立 Mock 的状态应保留；Mock 或其他附加组件只按本版明确说明更新。

## 五、升级后检查与故障处理

在 67 执行 `bash '<现场平台目录>/bin/standalone-health-check.sh'`，检查后端及 Flyway 启动日志、nginx、Worker 和现场独立生成器的运行状态、日志及心跳；确认升级后入口可访问，按本版清单完成业务验收。检查必要的实际表结构或数据，不能仅依据 Flyway 历史记录判断迁移成功。记录结果并确认原本运行的服务已恢复。

脚本的就绪检查失败时会尝试恢复旧程序，但**不会自动回退数据库**；启动脚本直接报错、安装外置脚本或备份阶段失败也不保证触发自动回滚。升级过程中任一步失败，应先检查进程、日志和 `rollback/`，确认服务状态并处理，勿反复盲目执行。程序回退不等于数据库回退；若迁移已执行，先评估旧程序与新结构的兼容性。需要恢复数据库时须停止相关写入、核对目标与备份，在隔离环境验证恢复方案后由授权人员在 67 操作，恢复会覆盖目标数据。不要对已有生产库导入初始化基线或重放历史迁移。

### Flyway 校验失败：现场存在仓库里没有的迁移

后端启动报 `Detected applied migration not resolved locally`（或 `Detected resolved migration not applied to database`）时，说明现场 `flyway_schema_history` 与升级包内 `BOOT-INF/classes/db/migration/` 不一致。处理顺序：

1. 先比对：`SELECT version,description,success,installed_on FROM flyway_schema_history ORDER BY installed_rank DESC;` 与包内迁移清单逐条对照，确认缺的是哪条、是否已被更高版本替代。
2. **不得删除或改写 `flyway_schema_history` 记录**，也不要手工补跑 SQL。
3. 若是现场独有的历史迁移且确已执行（如 `20261119174008 conservative health origin`），在 `config/app.env` 加精确到版本的白名单后重启：
   ```
   SPRING_FLYWAY_IGNORE_MIGRATION_PATTERNS=20261119174008:missing
   ```
   该参数只放宽校验，不会跳过任何待执行迁移；本次新增迁移仍会正常执行。后续把该迁移文件补回仓库后再移除这一行。
4. 若缺的是本版应交付的迁移，停止升级，核对升级包是否完整。

修改 `app.env` 后需重启后端生效，并在启动日志确认 `Schema ... is up to date`。
